# Azure deployment and release direction

The consolidated design, delivery sequence, budget assumptions, and proposed implementation details are in the [Azure deployment plan](../azure-deployment.md). This ADR records interview decisions; provisioning and pipeline implementation are separate work.

Mandatory execution policy: Agents may author and review Bicep, source code, CSV estimates, workflow definitions, operator scripts, documentation, and offline tests only. Every Azure account or resource operation must be performed by a human operator. Agents must not sign in to Azure, inspect the live account, run Azure what-if/apply, create/update/delete resources, change DNS/RBAC/secrets/firewalls, push/pull images through ACR, deploy apps, run migrations against Azure databases, restore data, or trigger Azure-affecting workflows. Main/tag CI may validate/build and retain artifacts outside Azure, but must not automatically perform Azure operations. Do not give unattended CI Azure credentials. Public documentation/pricing research and local tests without live Azure access are allowed. Human execution and live verification must be explicitly attributed and must not be claimed complete without operator-supplied evidence.

This later user instruction supersedes all earlier automatic Azure staging deployment and migration decisions. The agent implements authoring/offline checks only; a human performs all Azure execution and records live acceptance. See the deployment plan for the revised workflow.

Plan Azure hosting for Core API, Newlife Portal, and Facility Booking for approximately 200 users primarily in Canada, with fewer expected to be online concurrently. The available nonprofit grant is USD 2,000 per year across the deployment, with no self-funded overage planned. USD 166.67 per month is its arithmetic average, not a verified service estimate or an enforced spending cap. Grant eligibility, remaining credit, expiration, and subscription spending-limit behavior require verification before provisioning.

Updates to each repository's `main` and eligible version tags trigger CI/artifact preparation outside Azure only; release-branch updates run CI. A human selects and executes all staging and production deployments. Later main candidates may be manually deployed over staging without changing the settled production tag. Preserve independent versions and immutable source/artifact mapping. No agent or unattended CI may log in to Azure, publish to ACR, mutate infrastructure, migrate cloud databases, or trigger deployment.

Host Core API on Azure App Service for Linux using container images, with separate App Service Plans for staging and production. This replaces the earlier Container Apps hosting direction after its custom-VNet infrastructure costs exceeded the grant. Keep the plans independently configurable and scalable; use B1 per environment as the initial cost/load-test candidate, not a proven capacity requirement. Enable Always On to keep the existing expiry loop running. Basic plans do not provide deployment slots, so deployment and rollback must not assume slot swaps or zero downtime. Host Portal and Facility Booking on Azure Static Web Apps, using Free for staging and Standard from the initial production launch. Use separate Azure Database for PostgreSQL servers, Storage Accounts, and Key Vaults per environment, and share one Azure Container Registry with explicit image digest selection. Use one Static Web App per frontend per environment to bind the chosen custom hostnames.

Select Azure Managed Redis rather than the retiring Azure Cache for Redis service, preferring the smallest viable Balanced (Memory + Compute) SKU because the user expects a small dataset and prioritizes low cost. Use separate staging and production instances, with HA disabled for staging and enabled for production. Verify the smallest available Canadian SKU against the actual workload, client/clustering policy, and single-database constraint; adapt the current `db0`/`db10` separation before deployment. Exact SKU, connection policy, memory headroom, and regional capacity remain to be verified.

Use `api.efcnewlife.com`, `portal.efcnewlife.com`, and `booking.efcnewlife.com` for production, and `api.dev.efcnewlife.com`, `portal.dev.efcnewlife.com`, and `booking.dev.efcnewlife.com` for staging. Here the DNS label `dev` denotes staging, not local development. The user reports that `efcnewlife.com` is already managed in Azure DNS; this has not been independently checked against the Azure account. Configure the exact hostnames in DNS, TLS bindings, CORS, Entra redirect URIs, frontend builds, and application links.

Both staging and production migrations are now executed by a human from the exact target version, followed by human verification/deployment. Agents prepare scripts, compatibility checks, and offline tests only. A failed migration prevents the human from continuing rollout until resolved; do not assume partial schema changes automatically reverted. Keep migration revisions human-managed. Older-tag/newer-schema cases require compatibility checks without automatic downgrade or data reset.

Use PostgreSQL Flexible Server Burstable B1ms as the initial staging configuration and the production sizing candidate. Confirm production suitability through representative load testing before launch; low expected concurrency alone is not evidence of sufficient capacity. Include CPU credit behavior in validation. Plan staging as available around the clock for the initial cost estimate; scheduled shutdown or on-demand startup is not currently selected.

The initial file workload excludes video. Use Standard GPv2 Blob Storage, Hot tier, LRS, without hierarchical namespace. Use 10 GB as the first-year capacity assumption for cost estimation, not as a measured requirement or an enforced quota. Configure 14-day soft-delete protection and monitor actual growth. Do not infer capacity from the discarded estimate cost or from the absence of video.

Use Canada East as the preferred primary Azure region. Verify the selected services, SKUs, HA configurations, quotas, and prices there before provisioning; earlier Canada Central price research does not establish the Canada East budget. Prefer Canadian Azure regions for any necessary placement exceptions; this is a placement preference rather than a strict all-data residency requirement. Sentry is exempt from this preference. Service availability and any non-Canadian processing exceptions still require review.

Use independent repository release branches such as `release/0.3.0` and version tags such as `0.3.0`, without a `v` prefix. A production tag must identify a release-branch commit that passed CI. The human selects the tag, manually validates live database state, and executes production publication/deployment using the reviewed artifacts and runbook. CI prepares artifacts only and does not execute Azure commands. Permit human redeployment/rollback by selecting a previous compatible artifact without automatically downgrading the database. Tag protections and helper implementation remain authoring work.

The user is the primary operational contact and receives alerts by email. Overnight incidents can wait until the following day; no overnight immediate-response commitment is made. Accepted initial recovery objectives, to be verified by drills before launch, are application rollback within 30 minutes after response starts, database recovery within four hours after response starts, and a database recovery point within 15 minutes of the incident. Retain database backups for 14 days. Regional outages require a separate procedure without the same initial recovery-time commitment.

Before grant exhaustion, notify the user and reduce staging costs first. If the deployment still cannot remain within the grant, the user accepts pausing production until credit becomes available rather than funding an overage. Notification thresholds, the actual pause mechanism, residual storage/backup charges, and restart procedures remain to be designed; a budget alert alone does not enforce a spending cap.

Use Bicep with repository ownership split: Core API owns backend/shared infrastructure; each frontend owns its Static Web Apps/domains and release artifacts. Agents author and validate locally. Humans run Azure what-if/apply and every deployment. Keep CI without Azure credentials or unattended execution; humans establish required operator/runtime permissions and secret access.

Reference the existing `efcnewlife.com` Azure DNS zone rather than recreating it. Core API owns `api` and `api.dev` records; Portal owns `portal` and `portal.dev`; Facility Booking owns `booking` and `booking.dev`. Use separate repository deployment identities with permissions limited to the resources and DNS records they need to manage, subject to Azure RBAC capabilities. Backend secrets belong in the environment's Key Vault; public frontend build settings belong to the corresponding frontend configuration.

Keep API ingress public HTTPS and use App Service regional VNet integration to reach private data services. Blob remains browser-reachable with authorized/SAS access and anonymous access disabled. The human performs all setup, ACR publication, migration, deployment, inspection, and cleanup. No Container Apps migration Job, agent Azure access, unattended Azure workflow, permanent administration VM, or VPN is included.

Use PostgreSQL's `Public access (allowed IP addresses) and private endpoints` networking mode for both servers. API apps connect through Private Endpoints; developer debugging and production manual migration use the public endpoint restricted to explicit developer IP addresses, while staging migration is also human-run from an explicitly allowlisted operator IP. Do not use private VNet integration for these servers or enable broad public firewall exceptions. Keep Azure Managed Redis private-only with public network access disabled; the user no longer requests public Redis debugging access. A local Redis GUI tunnel is not an initial requirement. Account for four Private Endpoints in total, one per PostgreSQL and Redis instance, with the required Private DNS configuration, and reconcile their costs with the grant.

Revision 2026-11-10: to save about USD 31/month, the user removed all four Private Endpoints, the Private DNS zones, and App Service VNet integration. PostgreSQL uses public access with a firewall allowlist of the App Service possible outbound IPs plus explicit developer/operator IPs, with TLS; these outbound IPs are shared with other customers and can change. Azure Managed Redis offers no IP allowlist, so both Redis instances use public access from all networks with access-key or Entra authentication and TLS. This supersedes the Private Endpoint and private-only Redis decisions above. Sharing one Redis instance between staging and production is under consideration and not selected.

Revision 2026-11-12: the operator ran `az postgres flexible-server list-skus --location canadaeast` against the grant subscription and Azure answered "Provisioning is restricted in this region. Please choose a different region."; the same check for `canadacentral` returned no restriction. PostgreSQL must share a region with the API App Service, so the user moved every regional resource, for staging and production, from Canada East to Canada Central (Toronto). Canada Central is a Canadian region, so the Canadian placement preference still holds. This supersedes the Canada East primary-region decision above and the Canada East figures below. Canada Central has Availability Zones, but the HA choices are unchanged. Canada Central support for PostgreSQL 18 `Standard_B1ms`, Managed Redis `Balanced_B0`, and Linux App Service `B1` in the grant subscription remains a pending human check. The shared registry `efcnewlifecr`, already created in Canada East, cannot change region; the operator reported deleting it on 2026-11-12 and recreates it under the same name in Canada Central (see [`docs/azure-container-registry.md`](../azure-container-registry.md)). Static Web Apps has no Canada region, so the frontend placement exception is unchanged.

Service placement exceptions, sizing, live account/cost checks, and cloud validation are human acceptance gates. The proposed production runner read-only connection is not selected under the human-only policy. Agent deliverables must distinguish offline validation from pending human live evidence. No Azure resources or pipelines are provisioned by this decision. Preserve ADR 0038 telemetry/privacy rules.

## Budget basis and hosting tradeoff

The itemized estimate in [`infra/azure/cost/`](../../infra/azure/cost/README.md) supersedes the figures below. It gives about USD 1,530/year for the selected App Service baseline in Canada Central without Private Endpoints, before tax and other grant spend. The Canada East figures in this section are history.

The earlier approximate USD 145-160 monthly figures omitted the managed public IP and load balancer costs of Container Apps environments attached to a custom VNet. Do not use them as complete estimates. [Container Apps managed resources](https://learn.microsoft.com/en-us/azure/container-apps/custom-virtual-networks#managed-resources) documents these additional charges.

Canada East PAYG research using 730 hours per month, two external workload-profiles environments with Consumption apps, two API replicas at 0.5 vCPU/1 GiB, two PostgreSQL B1ms servers with 32 GiB each, three Balanced B0 Redis nodes, four Private Endpoints, two shared Private DNS zones, two production Standard Static Web Apps, shared ACR Basic, and small illustrative Blob/Key Vault/DNS usage gives approximately USD 210 per month (USD 2,520 per year) when API replicas mostly qualify for idle billing. This excludes several variable charges, including logs, processed network data, deployment overlap, and excess backup storage. Separate Container Apps environments are an estimation assumption, not a separately confirmed isolation requirement.

The network portion alone is approximately USD 81.30 per month: four Private Endpoints (USD 29.20), four Standard public IPs (USD 14.60), two Standard load balancers (USD 36.50), and two Private DNS zones (USD 1). Sources: [Private Link](https://azure.microsoft.com/en-us/pricing/details/private-link/), [IP addresses](https://azure.microsoft.com/en-us/pricing/details/ip-addresses/), [load balancer](https://azure.microsoft.com/en-us/pricing/details/load-balancer/), and [DNS](https://azure.microsoft.com/en-us/pricing/details/dns/) pricing. Actual consumption, subscription eligibility, and grant coverage remain unverified.

This rejected Container Apps estimate exceeds the grant before variable-cost headroom. Sharing one Container Apps environment lowers the illustrative idle total to about USD 184 per month and still exceeds the annual grant. This cost tradeoff motivated the user's App Service decision below.

The user selected Azure App Service with separate plans per environment instead of Container Apps or a shared App Service Plan. Canada East Linux B1 pricing of USD 0.018/hour per plan gives an illustrative total of about USD 156/month for two plans and the same data services/four Private Endpoints, excluding former Container Apps resources. Including the existing public DNS zone base charge gives approximately USD 1,876/year, before further usage; this is narrow headroom and not a guarantee of grant sufficiency. The deployment plan itemizes assumptions, usage sensitivity, and live account/cost checks. Sources: [Linux pricing](https://azure.microsoft.com/en-us/pricing/details/app-service/linux/), [VNet integration pricing](https://learn.microsoft.com/en-us/azure/app-service/overview-vnet-integration#pricing-details), and [hosting plan behavior](https://learn.microsoft.com/en-us/azure/app-service/overview-hosting-plans).

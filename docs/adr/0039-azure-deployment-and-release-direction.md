# Azure deployment and release direction

The consolidated design, delivery sequence, budget assumptions, and proposed implementation details are in the [Azure deployment plan](../azure-deployment.md). This ADR records interview decisions; provisioning and pipeline implementation are separate work.

## Release and migration decision — 2026-11-13 (EFC-322)

The [EFC-322 decision record](https://linear.app/jayhsia/issue/EFC-322) captures the alternatives and the final selection. CI migration and staging release-freeze proposals were rejected in favor of automatic staging application deployment with manual database work. This section supersedes the earlier blanket prohibition on CI Azure publication and staging deployment; it does not implement or enable a workflow.

The user selected automatic staging deployment after required CI succeeds on `main`, accepting that staging may temporarily become unstable while integrating changes. Feature branches merge into `main` through PRs; staging provides ongoing testing and verification. A short-lived `release/x.y.z` branch is cut from a selected, verified `main` commit to prepare production publication. Release-branch updates run CI without deploying from the branch event. Creating an eligible tag such as `0.3.0` on the release branch automatically deploys that exact tagged version to staging and prepares production release artifacts. There is no staging source-switch mode or release-validation freeze; later `main` updates may deploy over staging again.

The branch/release flow applies to `newlife-core-api`, `newlife-portal-frontend`, and `facility-booking-frontend`, with independent versions and releases. The shared UI package and infrastructure repository retain separate publication procedures. The ACR/App Service image steps below apply specifically to the Core API; the frontend hosting remains Static Web Apps.

For the Core API, both `main` and eligible tag workflows run required CI, build the exact source version's image, push it to ACR, and deploy the image to staging. On reconsideration, the user chose manual migrations for both staging and production because the application's scale does not justify CI database access and temporary firewall management. Workflows must not run live database migrations, obtain migration database credentials, or create runner database firewall rules. The user explicitly selected staging image deployment before manual staging migration, accepting possible temporary application failures while the schema catches up. Report initial deployment/smoke results without automatically rolling back. An initial workflow smoke result cannot substitute for successful verification after a required manual migration; the operator completes migration and verifies the deployed version before release acceptance.

Production does not use a deployment workflow: after the operator has completed required staging migration and the exact tag has passed staging deployment and smoke verification, the operator manually performs the production migration first, then changes the production App Service image tag to deploy that version. Production migrations must remain compatible with the old image while it is still running; stage destructive changes across releases. Record the immutable tag-to-commit-to-image-digest mapping and do not overwrite release image tags; production must resolve to the image verified on staging, independently of the version currently running there. A successful `main` run alone does not satisfy release verification. Neither creating the tag nor completing its workflow deploys production. The manual release procedure enforces migration verification; do not claim that CI checks live database revisions.

Use GitHub OIDC federation for workflow Azure login, with Azure RBAC limited to the ACR publication and staging deployment operations required by the jobs. Do not store a long-lived Azure client secret or grant the workflow production deployment or database migration access. Federation and exact role scopes remain infrastructure setup work for a human operator.

The operator runs migrations from an exact target checkout with locked dependencies (`uv sync --frozen`, then `uv run alembic upgrade head`), matching the source version of the deployed staging image or selected production image. No migration image or CI migration runner is selected. Runtime images continue to exclude Alembic files. Catalog bootstrap remains manual: after the first successful staging schema migration, the operator runs `init-all`, including its interactive superuser step. Do not run `init-all` in deployment workflows. Alembic revision files remain human-managed.

Release fixes start on a `hotfix/*` branch cut from the target release branch and merge back into that release branch through a PR. Publish the fix as a new patch version tag (`x.y.z` to `x.y.(z+1)`, for example `0.3.0` to `0.3.1`); never move or overwrite the previous tag. The new tag repeats staging rollout and verification before human-started production publication. Every hotfix must also be synchronized into `main`, using a separate branch and PR to carry the fix without bringing unrelated next-release changes into the release branch.

Image rollback does not revert the database schema. Prefer backward-compatible migrations and stage destructive changes across releases. A failed manual staging migration blocks release verification and production publication; a failed production migration blocks production image deployment. Never automatically downgrade or reset data. Staging image rollback is manual, replacing the earlier conditional one-time automatic rollback selection. A missing schema may explain initial smoke failure after deployment, so the operator completes migration and verification before deciding whether to roll back. Confirm previous-image compatibility with the current schema before a manual rollback; do not report the new version as validated while its required migration remains pending.

Exact OIDC/RBAC setup, deployment serialization implementation, compatibility evidence, and frontend publication mechanics remain implementation work in the existing release tickets, including [EFC-311](https://linear.app/jayhsia/issue/EFC-311). The cross-application spec is [EFC-291](https://linear.app/jayhsia/issue/EFC-291); no additional spec or implementation ticket is required for this decision. CI database access is not selected. No workflow or live acceptance is delivered by this document change.

## Execution boundary

Agents may author and review Bicep, source code, CSV estimates, workflow definitions, operator scripts, documentation, and offline tests only. Agents must not sign in to Azure, inspect the live account, run Azure what-if/apply, create/update/delete resources, change DNS/RBAC/secrets/firewalls, push/pull images through ACR, deploy apps, run migrations against Azure databases, restore data, or trigger Azure-affecting workflows. Public documentation/pricing research and local tests without live Azure access are allowed.

The selected CI exception is artifact publication and automatic staging application deployment using scoped OIDC federation after human setup. Infrastructure provisioning, identity/RBAC/secret/DNS/firewall setup, database administration and migrations, production deployment, recovery, and rollback remain human-operated. Human execution and live acceptance must be explicitly attributed and must not be claimed complete without operator-supplied evidence. Publishing this ADR or creating a PR does not authorize an agent to operate Azure.

## Hosting and operational decisions

Plan Azure hosting for Core API, Newlife Portal, and Facility Booking for approximately 200 users primarily in Canada, with fewer expected to be online concurrently. The available nonprofit grant is USD 2,000 per year across the deployment, with no self-funded overage planned. USD 166.67 per month is its arithmetic average, not a verified service estimate or an enforced spending cap. Grant eligibility, remaining credit, expiration, and subscription spending-limit behavior require verification before provisioning.

Host Core API on Azure App Service for Linux using container images, with separate App Service Plans for staging and production. This replaces the earlier Container Apps hosting direction after its custom-VNet infrastructure costs exceeded the grant. Keep the plans independently configurable and scalable; use B1 per environment as the initial cost/load-test candidate, not a proven capacity requirement. Enable Always On to keep the existing expiry loop running. Basic plans do not provide deployment slots, so deployment and rollback must not assume slot swaps or zero downtime. Host Portal and Facility Booking on Azure Static Web Apps, using Free for staging and Standard from the initial production launch. Use separate Azure Database for PostgreSQL servers, Storage Accounts, and Key Vaults per environment, and share one Azure Container Registry with explicit image digest selection. Use one Static Web App per frontend per environment to bind the chosen custom hostnames.

Select Azure Managed Redis rather than the retiring Azure Cache for Redis service, preferring the smallest viable Balanced (Memory + Compute) SKU because the user expects a small dataset and prioritizes low cost. Use separate staging and production instances, with HA disabled for staging and enabled for production. Verify the smallest available Canadian SKU against the actual workload, client/clustering policy, and single-database constraint; adapt the current `db0`/`db10` separation before deployment. Exact SKU, connection policy, memory headroom, and regional capacity remain to be verified.

Use `api.efcnewlife.com`, `portal.efcnewlife.com`, and `booking.efcnewlife.com` for production, and `api.dev.efcnewlife.com`, `portal.dev.efcnewlife.com`, and `booking.dev.efcnewlife.com` for staging. Here the DNS label `dev` denotes staging, not local development. The user reports that `efcnewlife.com` is already managed in Azure DNS; this has not been independently checked against the Azure account. Configure the exact hostnames in DNS, TLS bindings, CORS, Entra redirect URIs, frontend builds, and application links.

Use PostgreSQL Flexible Server Burstable B1ms as the initial staging configuration and the production sizing candidate. Confirm production suitability through representative load testing before launch; low expected concurrency alone is not evidence of sufficient capacity. Include CPU credit behavior in validation. Plan staging as available around the clock for the initial cost estimate; scheduled shutdown or on-demand startup is not currently selected.

The initial file workload excludes video. Use Standard GPv2 Blob Storage, Hot tier, LRS, without hierarchical namespace. Use 10 GB as the first-year capacity assumption for cost estimation, not as a measured requirement or an enforced quota. Configure 14-day soft-delete protection and monitor actual growth. Do not infer capacity from the discarded estimate cost or from the absence of video.

Use Canada East as the preferred primary Azure region. Verify the selected services, SKUs, HA configurations, quotas, and prices there before provisioning; earlier Canada Central price research does not establish the Canada East budget. Prefer Canadian Azure regions for any necessary placement exceptions; this is a placement preference rather than a strict all-data residency requirement. Sentry is exempt from this preference. Service availability and any non-Canadian processing exceptions still require review.

Use version tags without a `v` prefix and protect them against movement or deletion. A production tag must identify a release-branch commit that passed CI and the exact tag's staging acceptance. Permit human redeployment/rollback by selecting a previous compatible artifact without automatically downgrading the database. Tag protections and helper implementation remain authoring work.

The user is the primary operational contact and receives alerts by email. Overnight incidents can wait until the following day; no overnight immediate-response commitment is made. Accepted initial recovery objectives, to be verified by drills before launch, are application rollback within 30 minutes after response starts, database recovery within four hours after response starts, and a database recovery point within 15 minutes of the incident. Retain database backups for 14 days. Regional outages require a separate procedure without the same initial recovery-time commitment.

Before grant exhaustion, notify the user and reduce staging costs first. If the deployment still cannot remain within the grant, the user accepts pausing production until credit becomes available rather than funding an overage. Notification thresholds, the actual pause mechanism, residual storage/backup charges, and restart procedures remain to be designed; a budget alert alone does not enforce a spending cap.

Use Bicep in `newlife-infra` for all Azure infrastructure and associated operator runbooks. Each application owns its code, build/deployment workflows, and release artifacts. Agents author and validate locally; humans run Azure what-if/apply and establish operator/runtime and scoped CI federation permissions. CI publication and staging deployment follow the release decision above; infrastructure changes and production deployment remain human-run.

Reference the existing `efcnewlife.com` Azure DNS zone rather than recreating it. Infrastructure definitions for the API, Portal, and Facility Booking records belong in `newlife-infra`. Use separate repository workflow identities limited to artifact publication and staging application deployment; DNS changes remain human-run infrastructure work. Backend secrets belong in the environment's Key Vault; public frontend build settings belong to the corresponding frontend configuration.

Keep API ingress public HTTPS. Blob remains browser-reachable with authorized/SAS access and anonymous access disabled. Networking follows the 2026-11-10 revision below. No Container Apps migration Job, agent Azure access, permanent administration VM, or VPN is included.

The earlier private-network baseline used App Service VNet integration, four Private Endpoints, Private DNS, and private-only Redis. This is historical context only; the following cost decision superseded it.

Revision 2026-11-10: to save about USD 31/month, the user removed all four Private Endpoints, the Private DNS zones, and App Service VNet integration. PostgreSQL uses public access with a firewall allowlist of the App Service possible outbound IPs plus explicit developer/operator IPs, with TLS; these outbound IPs are shared with other customers and can change. Azure Managed Redis offers no IP allowlist, so both Redis instances use public access from all networks with access-key or Entra authentication and TLS. This supersedes the Private Endpoint and private-only Redis decisions above. Sharing one Redis instance between staging and production is under consideration and not selected.

Revision 2026-11-12: the operator ran `az postgres flexible-server list-skus --location canadaeast` against the grant subscription and Azure answered "Provisioning is restricted in this region. Please choose a different region."; the same check for `canadacentral` returned no restriction. PostgreSQL must share a region with the API App Service, so the user moved every regional resource, for staging and production, from Canada East to Canada Central (Toronto). Canada Central is a Canadian region, so the Canadian placement preference still holds. This supersedes the Canada East primary-region decision above and the Canada East figures below. Canada Central has Availability Zones, but the HA choices are unchanged. Canada Central support for PostgreSQL 18 `Standard_B1ms`, Managed Redis `Balanced_B0`, and Linux App Service `B1` in the grant subscription remains a pending human check. The shared registry `efcnewlifecr`, already created in Canada East, cannot change region; the operator reported deleting it on 2026-11-12 and recreates it under the same name in Canada Central (see [`docs/azure-container-registry.md`](../azure-container-registry.md)). Static Web Apps has no Canada region, so the frontend placement exception is unchanged.

Revision 2026-11-13: Azure rejected staging Managed Redis `Balanced_B0` and then `Balanced_B1` in Canada Central with `CacheCapacityUnavailable` during the operator's `what-if` preflight. The user accepted the nearest large US region, so staging Redis is placed in East US 2 as a recorded placement exception; every other regional resource stays in Canada Central. Each Redis call from the Canada Central App Service now crosses regions (roughly 15 ms per round trip, a few calls per request), and inter-region transfer adds a small charge. East US 2 is also the Static Web Apps candidate region, so this adds no new exception region. Production Redis placement is decided separately; try Canada Central first. The same day the user also chose `VolatileLRU` eviction instead of `NoEviction`: every Redis key has a TTL, a lost member refresh binding only forces a new sign-in, and refusing writes when memory is full would fail requests.

Revision 2026-11-13 ([EFC-308](https://linear.app/jayhsia/issue/EFC-308)): the operator created [`efcnewlife/newlife-infra`](https://github.com/efcnewlife/newlife-infra) as the single owner of Azure infrastructure. It supersedes the per-repository `infra/azure/` ownership proposed in the deployment plan; see [newlife-infra ADR 0001](https://github.com/efcnewlife/newlife-infra/blob/main/docs/adr/0001-newlife-infra-owns-azure-infrastructure.md). Moving the files changed no Azure resource. This spec and ADR stay in `newlife-core-api` as the cross-application decision record.

Service placement exceptions, sizing, live account/cost checks, and cloud validation are human acceptance gates. A production runner read-only database connection is not selected. Agent deliverables must distinguish offline validation from pending human live evidence. No Azure resources or pipelines are provisioned by this decision. Preserve ADR 0038 telemetry/privacy rules.

## Budget basis and hosting tradeoff

The itemized estimate in [`newlife-infra/azure/cost/`](https://github.com/efcnewlife/newlife-infra/blob/main/azure/cost/README.md) supersedes the figures below. It gives about USD 1,530/year for the selected App Service baseline in Canada Central without Private Endpoints, before tax and other grant spend. The Canada East figures in this section are history.

The earlier approximate USD 145-160 monthly figures omitted the managed public IP and load balancer costs of Container Apps environments attached to a custom VNet. Do not use them as complete estimates. [Container Apps managed resources](https://learn.microsoft.com/en-us/azure/container-apps/custom-virtual-networks#managed-resources) documents these additional charges.

Canada East PAYG research using 730 hours per month, two external workload-profiles environments with Consumption apps, two API replicas at 0.5 vCPU/1 GiB, two PostgreSQL B1ms servers with 32 GiB each, three Balanced B0 Redis nodes, four Private Endpoints, two shared Private DNS zones, two production Standard Static Web Apps, shared ACR Basic, and small illustrative Blob/Key Vault/DNS usage gives approximately USD 210 per month (USD 2,520 per year) when API replicas mostly qualify for idle billing. This excludes several variable charges, including logs, processed network data, deployment overlap, and excess backup storage. Separate Container Apps environments are an estimation assumption, not a separately confirmed isolation requirement.

The network portion alone is approximately USD 81.30 per month: four Private Endpoints (USD 29.20), four Standard public IPs (USD 14.60), two Standard load balancers (USD 36.50), and two Private DNS zones (USD 1). Sources: [Private Link](https://azure.microsoft.com/en-us/pricing/details/private-link/), [IP addresses](https://azure.microsoft.com/en-us/pricing/details/ip-addresses/), [load balancer](https://azure.microsoft.com/en-us/pricing/details/load-balancer/), and [DNS](https://azure.microsoft.com/en-us/pricing/details/dns/) pricing. Actual consumption, subscription eligibility, and grant coverage remain unverified.

This rejected Container Apps estimate exceeds the grant before variable-cost headroom. Sharing one Container Apps environment lowers the illustrative idle total to about USD 184 per month and still exceeds the annual grant. This cost tradeoff motivated the user's App Service decision below.

The user selected Azure App Service with separate plans per environment instead of Container Apps or a shared App Service Plan. Canada East Linux B1 pricing of USD 0.018/hour per plan gives an illustrative total of about USD 156/month for two plans and the same data services/four Private Endpoints, excluding former Container Apps resources. Including the existing public DNS zone base charge gives approximately USD 1,876/year, before further usage; this is narrow headroom and not a guarantee of grant sufficiency. The deployment plan itemizes assumptions, usage sensitivity, and live account/cost checks. Sources: [Linux pricing](https://azure.microsoft.com/en-us/pricing/details/app-service/linux/), [VNet integration pricing](https://learn.microsoft.com/en-us/azure/app-service/overview-vnet-integration#pricing-details), and [hosting plan behavior](https://learn.microsoft.com/en-us/azure/app-service/overview-hosting-plans).
